    components/ui Select, populated from api.getOrders().
    Renders "NF-10482 - Orbit Wireless Headphones" style labels.

[x] Chat with ChatBubble
    components/shared ChatBubble. Assistant left, customer right.
    16-message conversation tested end to end.

[x] Checklist of missing information
    components/shared Checklist. Five items: order, issue, description
    (10+ characters), photo, requested resolution. The photo row is
    overridden from the real uploaded file count rather than trusting
    the server value.

[x] Evidence upload - client-side type and size validation
    Validates JPG / PNG / PDF, 5 MB per file, 3 files maximum.
    Rejects with a specific message for each rule. Each chip is
    individually removable.

[x] CitationChip list
    components/shared CitationChip. Clicking a citation raises a Toast
    with the policy title and text. Verified rendering "P-3".

[x] Request preview card
    Order, issue, customer statement, evidence, requested resolution,
    and the 7-day window result ("Within 7-day window" /
    "Past 7-day window").

[x] Confirm and Submit - disabled until the preview is complete
    Rendered only when every checklist item is done, and the button is
    additionally gated on the preview existing.

[x] Confirm and Submit - generates an idempotency key
    crypto.randomUUID() per submission attempt, sent as the
    Idempotency-Key header. This matches the README requirement that the
    submit endpoint be idempotent.

[x] Confirm and Submit - disables on click so double-clicks cannot
    submit twice
    Three layers: `disabled={submitting}`, `loading={submitting}`, and a
    guard `if (submitting || trackingNo) return`. Once a tracking number
    exists the button is not rendered at all.

[x] Agent Timeline
    components/shared Timeline. Shows Intake, Policy and Resolution
    agent steps with outcome text, plus a customer-confirmed and
    case-created entry after submit.

[x] Tracking number success card
    Emerald card with the tracking number (for example AD-2026-0001) and
    a "View my cases" action.

[x] Existing-case card for S3 (repeated complaint)
    Shown when the response carries existingCase. Displays the tracking
    number and current StatusBadge instead of creating a duplicate.
    This is the README's "Detects an existing active case before
    creating another one".

[x] "Assistant is busy, retry" state
    Sending the word "busy" raises the llm_busy error, matching the
    README line "Rate limits and model failures preserve the draft and
    never show a false success". ErrorBanner offers Retry, which
    re-runs the stage without losing the draft.

[x] Mock scenario switcher - S1 Complete, S1 Incomplete, S3 Repeat,
    S4 Late
    Demo affordance only. See blocker B2 - it has no real-API
    equivalent.

5. BLOCKED / WAITING ON A PREREQUISITE
--------------------------------------------------------------------------------

B1. Real API integration - blocked on the backend task
    The single unmet "Done when" criterion. Setting VITE_USE_MOCKS=false
    today sends requests the README backend does not define:

      client.js                      README defines              result
      -----------------------------  --------------------------   --------
      GET  /orders                   GET /orders                 match
      GET  /cases                    GET /cases                  match
      GET  /chat/{scenario}          POST /chat                  MISMATCH
      POST /chat/{scenario}          POST /chat                  MISMATCH
      POST /cases/submit             POST /drafts/{id}/submit    MISMATCH

    Endpoints in the README table with no client method yet:
      GET  /me                             profile and role
      POST /drafts/{id}/attachments         upload evidence
      GET  /drafts/{id}                     draft and preview
      POST /cases/{id}/reply                reply to a staff request
      GET  /staff/cases                     staff search and filter
      PATCH /staff/cases/{id}/status        staff state transition
      GET  /files/{attachmentId}            authorised evidence

    Aligning client.js to the README table is the fix, but it should be
    done once against the working backend rather than twice. Until then,
    the mock layer is the only exercised path.

B2. Scenario switcher is mock-only
    "{scenario}" has no counterpart in the README API - the real flow is
    POST /chat with a message. The S1-S4 picker must be gated behind
    VITE_USE_MOCKS or removed for the live demo. Not a defect, but it
    must not ship visible in live mode.

B3. Reply box posts nothing
    CasesPage.sendReply uses a local setTimeout and never calls
    POST /cases/{id}/reply. Wired to a stub until the backend exists.

B4. Evidence upload stops at the browser
    Files are validated client-side and held in component state, then
    dropped on submit. They are never sent to
    POST /drafts/{id}/attachments. The README requires Firestore
    metadata plus local attachment storage on the server.

B5. Staff information request text is fixture data
    The "Staff requested more information" copy comes from
    mocks/fixtures.js, so it reflects whatever the fixture author wrote
    rather than a real staff message.

    NOTE: the backend task is referred to as "T9" because the Task 7
    brief says "T8 and T9 can start using only mocks". Confirm the
    actual task number before acting on this.

7. DEVIATIONS AND NOTES
--------------------------------------------------------------------------------

- File names. The task brief names pages/Support.jsx and
  pages/MyCases.jsx. The implementation is pages/SupportPage.jsx and
  pages/CasesPage.jsx, routed at /support and /cases. Naming convention
  matches the other pages. Worth reconciling before the staff task
  imports these paths.

- Customer case cancellation was removed. CasesPage previously offered a
  customer-facing "Cancel case" action that set status to Closed. This
  contradicted two explicit README statements: "The AI cannot ...
  change a case status", "Customers cannot change case status", and
  "Staff actions follow a validated case-status state machine". Removed
  so the frontend matches the documented trust model.

- Chat composer behaviour. The transcript was a min-height container, so
  it grew with every message and pushed the composer down the page until
  it sat under the footer. It is now a fixed-height scroll region
  (h-20rem / sm:h-24rem) with auto-scroll to the newest message, plus a
  mask-image fade so content scrolling under the top edge reads as
  intentional.

- Extra components used beyond the 2.7 list: Select and Dialog in
  components/ui, TypingIndicator in components/shared. All three are
  needed by these screens.
